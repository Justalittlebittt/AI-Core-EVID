# Repository agent operating rules

These rules apply to assistants, coding agents, and human operators performing repository tasks.

## Canonical development priority — prediction first (V3.2)

Use [Prediction-first Architecture V3.2](docs/PREDICTION_FIRST_ARCHITECTURE_V3_2.md) for **new mainline work**, including short user instructions such as “继续”. Earlier [Decision-first mainline](docs/MAINLINE_DECISION_FIRST.md) retains the legacy implementation inventory and existing engine contracts, but **prediction-first P0 priority takes precedence** over convenience-driven monitoring, audits, repeated historic PDF checks or another negative-factor sweep.

**One real outcome:** find decision-time A-share information that predicts future positive **after-cost executable benchmark-relative return**, demonstrate it on truly independent data, then deliver a dated real-security research / action case with uncertainty and existing buy/hold/exit discipline. No present signal has established this yet: **NO VERIFIED ALPHA / NO BUY**. Neither a green GitHub workflow nor a blocked-buy packet is a successful stock predictor.

When deciding what to do next:
1. Identify the highest-value **predictive or economic evidence gap**, not merely the newest broken script.
2. Prefer a grounded economic mechanism and valid new independent data to random factor substitution on an already-opened backtest archive; prior price rise must **never** become an implicit universal entry requirement.
3. Make a Problem Elimination Pass: delete, avoid, absorb or reuse before adding code, wrappers, CI, receipts or approvals.
4. Actually execute the nearest feasible experiment or deliver a source-backed real-issuer research case; disclose independent-OOS limits and never silently unblind protected data.
5. Preserve historical outcome/membership/time invariants, broker/lot costs, user stop-loss discipline, frozen 122/8 and V2.8.12 E studies, and no automated brokerage authorization. Do not alter frozen evidence to force progress.
6. Keep failed, preregistered factors closed; do **not** flip signs, retune thresholds or reuse opened outcome windows as fresh evidence.
7. Finish each work unit with an empirical result, a decision relevant to predicting/trading, or a precise evidence blocker. Do not mistake infrastructure completion for target completion.

**2026-11-19 evidence/target correction:** [V3.2 Predictive Evidence Reduction](research/V3.2_PREDICTIVE_EVIDENCE_REDUCTION_AND_DECISION_20261119.md) is the current evidence map. Do not mistake a 1-session MSE improvement for validated 20-session stock-selection profit. Before any new test, explicitly check that its target matches the 20-exchange-session, after-cost, tradable decision objective; otherwise label it strictly as a diagnostic and justify its expected decision value. With no new independent qualifying data or economic hypothesis, prefer existing source-bound real-issuer NO ACTION outputs to the next archive-factor sweep. No historical positive average can override the original DO_NOT_PROMOTE verdict.

No bulk deletion of existing historical scripts or Actions jobs is authorized by this priority update; only change code when the direct predictive/decision requirement is identified.

## Context-efficient continuation protocol (2026-11-20, active)

This section changes **agent interaction and retrieval scope**, not scientific or operational validity. Follow existing V3.2 priority and frozen contracts when they apply.

- **Short instruction / new chat entry:** For 股票预测 / AI Core EVID “继续”, first read `docs/ACTIVE_HANDOFF.md` and `AGENTS.md` (already supplied here). Read only the one or two source files needed for the selected next P0 work unit. Do **not** reconstruct every past conversation, re-read large research inventories, enumerate all workflows or fetch full logs by default.
- **Scope the checks:** For research continuation, examine the hypothesis, relevant decision-time inputs, original verdict and affected validations only. For an explicit Actions/incident/status request, follow `docs/operations/ACTIONS_STATUS_EVIDENCE_RULES.md` and `docs/contracts/OPERATIONS_NO_PASSIVE_WAIT_V1.md` fully; their actual-run evidence requirements remain mandatory. Do not interpret an ordinary prediction-development “继续” as a request to audit all schedules.
- **Execution batch:** Select a substantive P0 question, do a Problem Elimination Pass, execute feasible work, run relevant affected tests, correct observed failures, and commit evidence/state. Stop only on completion or a precise blocked boundary; do not end after a cosmetic micro-step. No silent background execution.
- **Persist, don't paste:** Keep source code, run artifacts, long diagnostics, frozen evidence and full decisions in GitHub. In chat provide only: objective, change/result, specific test evidence, blocker, and next action, with source links. Quote a full log or file only when essential to resolve an actual error or explicitly requested.
- **Handoff update:** After a substantive mainline change, update `docs/ACTIVE_HANDOFF.md` in the same change set, keeping it under ~100 lines and pointing to canonical proof rather than copying its contents. This is a concise locator, not a second source of truth or another gate. Never fabricate tests, fresh results, alpha status, or future outcomes just to keep it current.
- **Avoid uncontrolled growth:** Reuse an existing script/test/Action; add a new persistent workflow, broad defensive wrapper, extra approval or new audit only for a demonstrated gap. A nontrivial scientific or operational modification still requires appropriate full validation, regardless of context savings.

## GitHub Actions status and incident checks (mandatory)

Before reporting whether V2.8.4 Controlled Prospective E-Layer Observation, Infrastructure Smoke Diagnostic, or the daily monitor has run successfully, follow [the evidence-first status procedure](docs/operations/ACTIONS_STATUS_EVIDENCE_RULES.md).

In particular:
- Read schedule and current time first. Check actual GitHub Actions **runs**, not just commits.
- Inspect attempts and jobs; commit history alone misses pre-job failures.
- If the current connector cannot enumerate recent runs, use another authorized read-only route such as the existing GitHub-hosted daily monitor. Mark incomplete information `INCOMPLETE`, never `healthy`.
- Never repeat unchanged commit-only checks as if they prove no new failures.
- Distinguish infrastructure success from V2.8.12 prospective integrity and frozen research eligibility.
- Notify the user only under the declared incident/update thresholds; never invent a new event.

The monitoring procedure does not change scientific governance. Do not rerun a failed frozen task, modify frozen thresholds, inspect Fold3/Fold4, or assume V2.8.13 permission.

## No-passive-wait execution contract (P0, mandatory)

Follow [Operations No Passive Wait V1.0](docs/contracts/OPERATIONS_NO_PASSIVE_WAIT_V1.md) for every status, monitoring, recovery, or "continue" task. If work is executable now, a response ending merely in "waiting for the next schedule/data" is an `OPERATIONAL_PROCESS_FAILURE`. Time gates apply only to external future observations, not independent diagnostics. Complete the evidence gate, available-work scan, permitted execution, validation, and termination gate before concluding. Do not change frozen research contracts to satisfy this operational rule.
